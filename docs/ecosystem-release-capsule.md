# Three-repository installed-wheel release capsule

Prob4D, BayesianPhysTwin, and Causal4D exercise an installed-wheel golden path
owned by BayesianPhysTwin. Prob4D's `Ecosystem installed-wheel release capsule`
workflow wraps that path in a content-addressed evidence capsule.

The workflow checks out one exact revision of each repository, builds one wheel
from each clean source snapshot, installs only those wheels into an isolated
Python environment, and runs the complete three-repository integration suite.
The suite already covers:

- a Prob4D observation accepted by BayesianPhysTwin;
- a baseline-relative regret-guard acceptance;
- a guard rejection that preserves exact baseline bytes;
- a lineage-bound BayesianPhysTwin belief consumed by Causal4D;
- a deterministic Causal4D physical posterior;
- consumer rejection of malformed or semantically drifted observations; and
- a content-addressed, promotable infrastructure run manifest.

Capsule schema version 2 binds those concrete artifacts rather than recording only
that the test command passed.

## Bound evidence

The installed-wheel tests materialize exactly these files:

- `exact-prob4d-observation.npz`;
- `profile-bound.npz`;
- `lineage-bound-twin-belief.npz`;
- `lineage-bound-physical-posterior.npz`;
- `run-manifest-v2.json`;
- `accepted-selection.json`;
- `rejected-selection.json`;
- `golden-path-bundle.json`; and
- `public-api-manifest.json`.

The last file is generated by a Prob4D-owned integration test from the **installed
Prob4D wheel**, after the BayesianPhysTwin evidence writer has completed. It records
the exact compatibility-root, `prob4d.api.v1`, and `prob4d.api.v2` export
inventories and provider API versions for the wheel that actually ran.

Before a capsule can be written, the builder independently verifies:

- the public API manifest's schema, package identity, surface semantics, and
  content identity;
- the run manifest's content identity and timestamp-independent evidence
  fingerprint;
- both selection artifacts' content identities and decision semantics;
- exact candidate bytes for acceptance;
- exact baseline bytes and fallback identity for rejection;
- equality between standalone selection files and the embedded decision bundle;
- equality of observation, belief, posterior, provider, run, and evidence IDs
  across both decisions;
- equality of repository revisions with the checked-out source snapshots;
- equality of wheel hashes with the wheels reported by the isolated golden-path
  installer; and
- equality of the public API package version with the installed Prob4D package
  version recorded by the decision artifacts.

The capsule also records the SHA-256 digest and byte size of every evidence file
and the golden-path log. Verification can therefore be repeated against the
retained execution bytes, not only against the compact JSON capsule.

## Capsule contents

`ecosystem-release-capsule.json` records:

- the exact three repository revisions;
- each built wheel filename and SHA-256 digest;
- the provider, observation, public API, decision-bundle, and run-manifest
  contract versions;
- the installed-wheel public API manifest ID;
- the run-manifest ID and evidence fingerprint;
- the accepted and rejected decision artifact IDs;
- the exact fallback identity;
- the observation, twin-belief, physical-posterior, and provider-manifest IDs;
- every retained evidence-file digest and byte size;
- the Python and runner identities; and
- the GitHub Actions run identity.

The top-level `capsule_id` is computed from canonical JSON. Any changed revision,
wheel bytes, public API inventory, decision, fallback bytes, downstream handoff,
retained evidence file, contract version, or execution identity therefore
produces a different capsule.

## Running the workflow

Use the workflow's manual dispatch and select the BayesianPhysTwin and Causal4D
branch, tag, or commit to validate. The selected refs are resolved to exact commit
SHAs before the capsule is written. Prob4D is always the exact reviewed workflow
revision: a pull-request head on pull-request events and `github.sha` otherwise.

The workflow also runs weekly and whenever the release-capsule implementation,
Prob4D-owned integration tests, public API manifest, or stable provider/observation
boundaries change.

The uploaded workflow artifact retains:

- `ecosystem-release-capsule.json`;
- `ecosystem-golden-path.log`; and
- the complete nine-file evidence directory.

## Local capsule tooling

Seal a retained execution with:

```bash
python scripts/ci/build_ecosystem_release_capsule.py build \
  --golden-path-log ecosystem-golden-path.log \
  --evidence-root retained-golden-path-evidence \
  --prob4d-revision <40-hex-commit> \
  --bayesian-phystwin-revision <40-hex-commit> \
  --causal4d-revision <40-hex-commit> \
  --python-version 3.12.11 \
  --runner-os Linux \
  --run-id 123456789 \
  --run-attempt 1 \
  --run-url https://github.com/IPS-Stuttgart/Prob4D/actions/runs/123456789 \
  --output ecosystem-release-capsule.json
```

Deeply validate the capsule structure and content identity:

```bash
python scripts/ci/build_ecosystem_release_capsule.py verify \
  ecosystem-release-capsule.json
```

Revalidate it against the exact retained log and evidence bytes:

```bash
python scripts/ci/build_ecosystem_release_capsule.py verify \
  ecosystem-release-capsule.json \
  --golden-path-log ecosystem-golden-path.log \
  --evidence-root retained-golden-path-evidence
```

The builder rejects missing or extra evidence, symbolic links, nonregular files,
duplicate JSON keys, nonfinite values, malformed revisions and hashes, conflicting
wheel records, unknown fields, altered API surfaces, forged run fingerprints,
inconsistent decision bundles, inexact fallback, and capsules whose identities do
not reproduce from their declared content. Publication is atomic and does not
replace a different existing capsule.

## Claim boundary

A passing capsule proves that the declared installed wheel bytes interoperated
through the retained accepted-update, exact-fallback, and Causal4D handoff paths,
and that the exact evidence bytes remain bound to the capsule. It is
infrastructure and provenance evidence only. It does not establish Prob4D
observation accuracy, calibrated uncertainty, BayesianPhysTwin physical-query
improvement, Causal4D intervention benefit, deployment safety, or state of the
art.
