# Prob4D 0.4.0 release boundary

Prob4D 0.4.0 is the first release boundary that covers the complete sparse
observation path from a causal gauge-tree prior through portable claim-bearing
artifacts and guarded BayesianPhysTwin consumption.

## Main additions

- Content-addressed `O(K)` causal gauge-tree prior artifacts with bounded,
  descriptor-stable loading.
- Tree-backed sparse observation-factor stacks that preserve the exact gauge
  precision without constructing or serializing the complete joint covariance.
- Portable and claim-bearing tree-sparse observation artifacts with provider,
  calibration, runtime-revision, causal-lineage, and sparse-prior identities.
- Target-blind provider support feasibility before residual generation, including
  complete stream, geometry, camera, metric-anchor, admission, and technical
  exclusion semantics.
- Spatially stratified causal tracklets and frozen-roster camera-panel support
  with a frame-level likelihood-power budget.
- Replay-complete held-out provider evidence binding calibration selection, exact
  provider-report bytes, target decisions, exact fallback, bootstrap settings,
  and the final Prob4D-to-BayesianPhysTwin promotion report.
- Paired joint-covariance dependence ablations that distinguish full shared
  covariance from marginal-preserving independence and conditional-only controls.
- One canonical grouped CLI with registry-driven compatibility wrappers and
  exact migration guidance for historical `prob4d-*` executables.
- A versioned `prob4d.api.v1` façade for downstream Python consumers, with the
  package version resolved from installed metadata instead of duplicated release
  constants.
- A package-only source distribution that is installed and smoke-tested in an
  isolated environment; workflows, tests, generated evidence, and CI machinery
  remain in the repository or separate evidence capsules.

## Compatibility

Provider API v1 remains frozen for exact reproduction:

- its `ObservationFactorBundle` declaration remains schema 3;
- its content-addressed manifest retains the historical repository and
  `prob4d.provider_v1` import-boundary fields;
- its historical finite-difference and compatibility semantics remain unchanged;
- legacy executables remain installed during the current pre-1.0 compatibility
  period.

Provider API v2 continues to advertise schema-4 joint-gauge bundles. The
extended tree-sparse provider manifest additionally advertises the portable
`TreeSparseObservationArtifactV1` and claim-bearing envelope contracts.

The current canonical repository is `IPS-Stuttgart/Prob4D`, represented through
the transfer-resistant project-identity descriptor. Historical artifact aliases
remain accepted without rewriting content-addressed bytes or identities. New
downstream Python code should import `prob4d.api.v1` rather than the broad package
root or experiment-specific modules; this façade is additive and does not alter
the frozen provider manifests.

## Downstream boundary

BayesianPhysTwin consumes claim-bearing tree-sparse artifacts through strict
admission and an exact tree-block Schur solver. Rejected or non-converged updates
retain the unchanged physical/prior fallback. Causal4D consumes the resulting
versioned belief rather than reinterpreting raw Prob4D factors.

## Scientific claim boundary

This software release establishes implementation, artifact, replay, memory,
compatibility, and fail-closed admission properties for the declared contracts.
It does not establish real-provider competence, calibrated uncertainty on a new
physical cohort, BayesianPhysTwin benefit on fresh objects or sessions, Causal4D
intervention benefit, deployment safety, or state of the art.

The retrospective 19-interaction MotionCrafter result remains negative, and the
official-Hub Deform360 provider version remains terminal at the pre-residual
support boundary (`313/324` supported streams, 11 support-negative streams,
zero technical failures). No confirmation payload was opened for that route.

## Publication

The complete 0.4.0 state is committed directly and reviewed normally. No workflow
mutates or pushes its own source branch. Merging this change synchronizes source,
distribution, citation, provider manifests, changelog, tests, and CI declarations.
It does not publish to a package registry or create a Git tag. Those actions
require a separate explicit release operation against the reviewed merge commit.
